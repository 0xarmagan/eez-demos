## What the scenario actually is

A flash loan whose repayment depends on a full L1→L2→L1 bridge round trip,
**inside one L1 user transaction**. Per its own header:

- `pool.flashLoan(token, 10k)` → `executorL1.onFlashLoan()`
- **L1 entry 0** — `bridge.bridgeTokens(...)` locks 10k in `bridgeL1` and calls
  the L2-bridge proxy. Key: bridge→bridge `receiveTokens` forward.
- **L1 entry 1** — `executorL2Proxy.call(claimAndBridgeBack)`. Its single
  top-level `l2ToL1Call` is the **return leg**: `bridgeL2`→`bridgeL1`
  `receiveTokens` runs on L1 and releases the escrowed 10k back to `executorL1`.
- Repay the pool — solvent **only because** the return leg released the escrow.

That is the differentiator claim in executable form: not a message that arrives,
but a value released mid-transaction that decides whether the transaction can
complete.

## The "step 5 encoding asymmetry" — resolved, and the answer is the inverse of the fear

The plan calls this *"the likeliest defect in the whole plan"* and makes
protocol review of it a publish blocker. Here is the actual state at the pin.

The scenario computes the **same logical return call two ways**:

```solidity
// _retHash — the L1 side
crossChainCallHash(false, a.bridge, L2_ROLLUP_ID, a.bridge, MAINNET_ROLLUP_ID, 0, _retReceiveData(a))

// _retHashL2Out — the L2-outgoing side
crossChainCallHashL2Out(a.bridge, L2_ROLLUP_ID, a.bridge, MAINNET_ROLLUP_ID, 0, _retReceiveData(a))
```

Two helper names, and a writer's instinct is that the return leg keys
differently. **It does not.** `crossChainCallHashL2Out` is a one-line wrapper:

```solidity
return crossChainCallHash(false, sourceAddress, sourceRollupId, targetAddress, targetRollupId, value, data);
```

They are byte-identical today, and the run confirms it empirically — the L1 and
L2 expected-hash lists are the same two values:

```
L1 expected calls: [0x4a58e920…66e2, 0x4018c880…44c5]
L2 calls expected: [0x4a58e920…66e2, 0x4018c880…44c5]
```

**So the asymmetry is latent, not live**, and the separate helper exists as a
marker. Its own doc comment says why:

> the sites to touch if `useGasLeft` flips on; the devnet runs false, so
> `callGas` folds 0

That makes the guide's correctness condition precise, and it is a trap in both
directions:

- Writing *"the return leg is hashed differently"* is **wrong today** — the two
  hashes coincide.
- Writing *"one call, one hash"* is **right today and wrong the moment
  `useGasLeft` flips on**, because calls leaving an L2 would then fold
  `uint64(gasleft())` while every other site keeps folding 0.

The honest sentence is that the two are the same function today, deliberately
named apart so the L2-outgoing sites are findable when gas keying turns on. This
is the same fact `q5` now teaches under card 0.5, seen from the harness side, and
`DeployManagerL2` corroborates it a third way: `new EEZL2(rollupId,
systemAddress, false)`.

**Recommendation:** step 5 still wants protocol-engineer sign-off, but the
question to put to them is now specific rather than open — *"is it correct to
document the L2-outgoing key as identical to the L1 key today, and flag
`useGasLeft` as the single condition that separates them?"* That is a
yes/no, not a review.

## Cold-start defect: the harness does not run on stock macOS

Relevant to card 1.3, whose cold-start test says *"every stop is a defect"*.
Two distinct bash-3.2 incompatibilities, and macOS ships bash 3.2.57:

1. **`declare -A`** (associative arrays, bash 4+) — `E2EBase.sh:182`, plus three
   sites in `decode-trace.sh`. Fails as
   `declare: -A: invalid option`.
2. **`set -u` with empty array expansion** — bash 4.4+ treats an empty array as
   defined; 3.2 does not. Hit as `_E2E_PIDS[@]: unbound variable` and
   `chain_arg[@]: unbound variable`.

Both are in reporting paths, not execution, so the workaround is local and the
run above is otherwise untouched: drop `-u`, and drop the `VERIFY_STEP_OUT`
stash. CI would never catch this — the runners execute on ubuntu, where bash is
5.x.

Worth raising upstream as a portability issue rather than carrying a patch:
either `#!/usr/bin/env bash` should be a version check with a clear message, or
the four `declare -A` sites should be replaced. A macOS developer following
`script/e2e/README.md` today gets an opaque `declare: -A: invalid option` on the
first command and no indication why.

## What still needs the live devnet

Only the network-mode half, and only for two things: the **captured trace** and
the **gas numbers** feeding 4.2. Local mode has the test playing sequencer and
posting batches itself, so it cannot produce composer-side timing or real gas.
Everything about the encoding — the part the plan feared most — is now checkable
without it.
