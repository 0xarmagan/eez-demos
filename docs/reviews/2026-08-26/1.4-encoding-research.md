# Card 1.4 — encoding research, timebox spent

**Verdict: 1.4 overflows the timebox. Drop it to Wave 2.** The card's own instruction
covers this: *"encoding research timebox = 1 day, overflow → Wave 2, never guess."*

Not because the idea is wrong. Because **the protocol supports N=2 and the e2e
harness does not**, and closing that gap is protocol-engineering work rather than
content work.

## First, the card's input path is wrong

> inputs: `script/e2e/multi_call/` at `node_pin` — read **before** drafting

`script/e2e/` is not in `eez-rollup0`. It is in **`eez-core-protocol` at
`9735f53`** — the contracts pin, not the node pin. The directory holds `.s.sol`
Foundry scripts, which is the tell.

## What the harness actually is

`script/e2e/<category>/<direction>/<scenario>/`. Six categories (`one_way`,
`multi_call`, `multi_tx`, `nested`, `reentrant`, `revert`) and — per its own
README — exactly two directions: **`L1_to_L2` and `L2_to_L1`**.

22 scenarios at the pin. **None of them involves two L2s.** There is no
`L2_to_L2` directory and no scenario that names a second rollup id.

## The five things that block 1.4 as written

1. **No L2↔L2 direction exists.** The README states the direction set outright;
   the tree confirms it.

2. **The infra deploys exactly one rollup.** `script/e2e/shared/DeployInfra.s.sol`
   registers a single `Rollup` and asserts it:
   `require(rid == 1, "expected L2 rollupId = 1")`.

3. **The config carries one L2.** `chain.env` in the README has a single
   `L2_RPC`, `L2_FRONT` and `MANAGER_L2`. The Kurtosis devnet is the same shape:
   `testing/kurtosis/ci-args.yaml` has one `l2_block_time_ms` / `l2_system_key`
   and no second-L2 block.

4. **The only batch builder is single-rollup, by name and by construction.**
   `immediateSingleRollupBatch` (`E2EHelpers.sol:232`) hardcodes
   `new RollupIdWithProofSystems[](1)` and
   `expectedStateRootPerRollup: new ExpectedStateRootPerRollup[](0)` — no
   cross-rollup state-root pins. There is no multi-rollup variant in the file.

5. **"multi-call-two-diff" is not two rollups.** This is almost certainly what
   the card was reaching for, and it means two different *target contracts* on
   one L2: both entries carry `destinationRollupId: L2_ROLLUP_ID`, and both
   `StateUpdate`s carry `rollupId: L2_ROLLUP_ID`. The header comment says so —
   *"two different targets, one L1 tx → two L2 deliveries"*.

## The protocol, by contrast, does support N=2

Worth stating so this reads as a tooling gap and not a protocol limit:

- `RollupIdWithProofSystems[]` and `ExpectedStateRootPerRollup[]` are arrays.
- `EEZ.sol` carries `_containsRollupInList(verifiedRollups, …)`,
  `RollupNotInBatch(uint64 rollupId)`,
  `StateUpdatesNotStrictlyIncreasing(uint64 rollupId)` and
  `ExpectedStateRootsNotStrictlyIncreasing(uint64 rollupId)` — all of which only
  mean anything with more than one rollup in a batch.
- `docs/CAVEATS.md` states the rule directly: cross-rollup interactions inside
  the meta hook are supported **between rollups verified together in the same
  batch**.

That last line is also the card's required *"same batch follows"* caveat, already
grounded and citable for whenever 1.4 is built.

## What building 1.4 would actually take

A second `Rollup` + `registerRollup` + `EEZL2` in `DeployInfra`, a second L2 in
`chain.env` and in the Kurtosis args, a multi-rollup batch builder to replace
`immediateSingleRollupBatch`, and the `expectedStateRootPerRollup` pins that
builder currently passes as empty. None of that is content work, and none of it
should be guessed at in a walkthrough.

## Two findings that land outside 1.4

**`useGasLeft` is false in every fixture.** `DeployManagerL2` constructs
`new EEZL2(rollupId, systemAddress, false)`. This independently corroborates
spec §C — *"Under `useGasLeft = false` (current deployments and all test
fixtures) every site folds 0"* — which is what card 0.5 now teaches on `q5`.

**Card 1.2 has more ground truth than the plan knew, and may be less blocked.**

- There is an upstream flash-loan e2e scenario:
  `script/e2e/nested/L1_to_L2/flash-loan/E2EFlashLoan.s.sol`, alongside
  `src/periphery/defiMock/FlashLoan.sol` and `FlashLoanBridgeExecutor.sol`. The
  banked `flash-loan-guide.md` is still missing, but the guide does not have to
  start from nothing.
- The harness has **two modes**, and the README is explicit that local mode needs
  no setup: *"Local — everything on anvil; the test itself plays sequencer and
  posts batches."* So the scenario can be exercised with
  `bash script/e2e/run/local-parallel.sh nested` on anvil, with no devnet.
- 1.2's done-when names `script/e2e/run` — the runners are
  `local.sh`, `local-parallel.sh`, `network.sh`, `network-parallel.sh`,
  `network-sequential.sh`, `prepare-network.sh`.

What still needs the real devnet is the **network-mode** half of 1.2 — the
captured trace and the gas numbers that feed 4.2, since local mode has the test
playing sequencer rather than a live composer. The encoding itself can be read
and checked against a local run first, which is the part the plan flagged as
*"the likeliest defect in the whole plan"*.
