## The fix already applied — `1db1f08`

`snippets/q2-cross-chain-call.sol:40` declared `STATIC_CHECK_GAS = 5000`. Upstream `CrossChainProxy.sol:23` is `uint256 private constant STATIC_CHECK_GAS = 1_000;`. A reader copying the panel would have forwarded five times the gas upstream forwards, on every cross-chain call, forever — and in a static context the `tstore` is an exceptional halt that consumes **everything** forwarded to it, so the cap is not a ceiling, it is the price.

Fixed in all three shipped copies: the snippet (`snippets/q2-cross-chain-call.sol:40`), the embedded `fullSnippet` (`dapp-developers/q2-send-a-cross-chain-call.html:361`), and the generated file (`llms-full.txt:277`). A repo-wide grep for `5000` / `5_000` now hits only the review plan. The `assembly { tstore(0, 1) }` in `staticCheck()` is now labelled a stand-in for upstream's named `uint256 transient _staticDetector` (`CrossChainProxy.sol:18`, written at `:71`), with the reason spelled out: raw slot 0 is not reserved for you, so in a contract that also uses transient storage the probe is a collision risk.

Verified after the fact: diff is +39/−3 across exactly those three files; `build-llms.py` and `sync-embedded-snippets.py` both regenerate byte-identically, so nothing unintended was absorbed; and all three checkers pass — `check-panel-drift.py` 7 pages / 551 panel lines, exit 0; `verify-citations.py` 25 citations / 27 assertions, exit 0; `audit.sh` "Structural audit passed", exit 0.

**Why it survived every gate.** `check-panel-drift.py` compares the panel to the snippet; `verify-citations.py` compares the cited line to upstream. The constant's **value** appears in neither surface, because the panel shows only `gas: STATIC_CHECK_GAS`. Panel and snippet agreed with each other, the citation pointed at a real line, and the wrong number sat between them untouched. Task 8 exists to close exactly this.

## Blocking

### B1 — `q2` teaches the cross-chain call without the same-block constraint, and the rule is side-specific

`EEZ.sol:794-797`, the first thing after the registry guard in `executeCrossChainCall`:

```solidity
// Entries can only be consumed in the block they were posted
if (verificationByRollup[destRid].lastVerifiedBlock != uint64(block.number)) {
    revert ExecutionNotInCurrentBlock(destRid);
}
```

`q2` never mentions it. A grep of the page for `block`, `batch` or `verif` returns four hits: three CSS comments and one entry in the syntax highlighter's keyword table (`:440`). There is no mention of blocks, batches or verification timing anywhere on the page, while step 3's diagram (`:201-204`) shows the manager dispatching to `IRemote.setValue(42)` unconditionally and captions it *"Runs with the proxy as msg.sender — real return data or revert bubbles straight back to you"* (`:206`).

This is the constraint that kills designs assuming "later." It belongs on the page that teaches sending the call.

**The precision that must survive into the copy: the asymmetry is L1-only.** `staticCrossChainCall` (`EEZ.sol:1266-1328`) has no block gate on L1 — `:1308-1310` falls straight through to `verificationByRollup[destRid].staticEntryQueue`, and the source says why in its own comment: *"Note that static calls do not obsolete after a block passes. As long as the state roots matches it can be execute"*. But `EEZL2.sol:634` **does** gate the L2 static path — `if (lastLoadBlock != block.number) revert ExecutionNotInCurrentBlock();` — with the docstring at `:588` explaining it: *"no pins on L2 — the block gate bounds staleness"*.

`q2` teaches the shared `CrossChainProxy`, which runs on both sides. So the added text must not say flatly that static calls are, or are not, block-gated.

**Fix:** one sentence at step 3, scoped: mutating cross-chain calls are consumable only in the block their entry was posted (`ExecutionNotInCurrentBlock`); static calls are gated on L2 but not on L1, where a static entry stays valid as long as the state root matches.

## Protocol accuracy

- **A1 — `q2` uses retired vocabulary for the static path, twice.** `captions[2]` (`:276`) — *"routed to a read-only lookup instead of a real execution"* — and the WHAT YOU'LL LEARN item 03 (`:240`) — *"routed to a read-only lookup"*. A grep of `EEZ.sol`, `EEZBase.sol`, `IEEZ.sol` and `CrossChainProxy.sol` at the pin returns four `lookup` hits, all generic English (`reverse-lookup mapping` ×3, `log(n) lookup`); none names the static path. The current name is `staticCrossChainCall` (`EEZ.sol:1266`), resolving a `StaticExecutionEntry` (`:1309-1324`) — and the panel beside this prose already says `IEEZ.staticCrossChainCall` (`:305`), so the page contradicts itself in the same viewport. This is `LookupCall` → `StaticExecutionEntry` vocabulary that the `feature/simplify` refactor retired; it means the source it was written from is stale. → caption: *"One self-call probes a transient write. If it reverts, this is a read — routed to `staticCrossChainCall`, which resolves it against a pre-computed static entry instead of executing."* → learn item: *"One self-call probes a transient write — a revert marks it a read, routed to the static path."*
- **A2 — `q2`'s caller never checks the result, and the FULL view is no better than the panel.** `snippets/q2-cross-chain-call.sol:27-28` is `(bool ok, ) = proxyAddress.call(data);` then a bare `ok;`. `codeByStep[1]` (`:290`) shows only the first of those two lines — but the second is not a check either, it is a no-op that silences solc's unused-local warning. So nothing anywhere in `q2` ever tests the result. Not Blocking: nothing displayed is false and no security boundary is misstated. It is an unsafe idiom shipped uncommented, and it is worse here than in ordinary Solidity, because a cross-chain `.call` fails for reasons a same-chain call cannot — see B1 and W1. → `if (!ok) revert CrossChainCallFailed();` with a named error, which is `q3`'s own stated rationale for custom errors applied one page earlier.
- **A3 — `q7`'s caption 3 attaches to the wrong function by adjacency.** `captions[2]` (`:290`): *"Remote addresses only. A proxy for your own network reverts."* True of `createCrossChainProxy` — the guard is `EEZBase.sol:166`, `if (originalRollupId == _getRollupId()) revert SameNetworkProxy(originalRollupId);`, inside `_createCrossChainProxyInternal`. False of `computeCrossChainProxyAddress` (`EEZBase.sol:176-185`), which is `public view`, has no guard, and reverts on nothing. `q7`'s `codeByStep[2]` (`:313-327`) is cumulative: the `createCrossChainProxy` signature at indices 0-3, the `computeCrossChainProxyAddress` signature at 5-8, then the bare guard at 10-12 with **no enclosing function header** — and `hlByStep[2] = [10,11,12]` (`:342`) highlights the guard directly beneath the signature it does not belong to. Two mitigators, stated fairly: the step-3 diagram scopes it correctly (`createCrossChainProxy` → ALLOWED / REVERTS), and `citeByStep[2]` (`:337`) correctly re-points to `EEZBase.sol:166`. So this is an ambiguity of adjacency, not a false statement. It still misleads on the one page whose whole subject is which of the two functions to call. → *"Remote addresses only — `createCrossChainProxy` reverts `SameNetworkProxy`. Note `computeCrossChainProxyAddress` does not: it will hand you an address for a proxy that can never exist."*
- **A4 — `q3`'s test overclaims in its own comment.** `snippets/test/Q3MsgSender.t.sol:27-28`: *"Stands in for the manager. Uses the real derivation so the proxy address in the test is the one the protocol would actually produce."* The second clause is false for two independent reasons: `:36` hashes `type(Dummy).creationCode`, not `CrossChainProxy`'s, so the init-code hash differs; and `address(this)` is the `MockEEZ` test contract, not a real manager, so the address would differ even with the right creation code. The first clause survives — the formula **is** the real one (`EEZBase.sol:181-184`). ## What this gets right

- **R1 — `q3`'s security claim is verified in both halves, and stated at the point of the fix rather than in a footnote.** *(a) Derivation.* `EEZBase.sol:167` sets `salt = keccak256(abi.encodePacked(originalRollupId, originalAddress))`; `:181-184` takes `bytecodeHash` over `type(CrossChainProxy).creationCode` + `abi.encode(address(this))` and CREATE2s with the manager as deployer — so the manager appears twice, as deployer and as constructor argument. Worth recording explicitly: `abi.encodePacked(uint64, address)` is collision-free here because both operands are fixed-width (8 + 20 = 28 bytes, no ambiguous boundary). Packed-encoding collisions are the usual trap in exactly this shape, and this one avoids it. *(b) Impersonation.* `CrossChainProxy.sol:50-63`: `executeOnBehalf` forwards to an arbitrary destination **only** under `:51` `if (msg.sender == EEZ)`. Every other caller falls through to `_fallback()` at `:62`, which calls the *manager* with the real `msg.sender` as `sourceAddress` (`:97` / `:101`) and never wears the proxy's identity toward a destination. A stranger can never make the proxy call a destination of their choosing. *Footnote of fact, explicitly not a qualification:* the constructor at `CrossChainProxy.sol:31-34` does make one call — `if (predeployedEther != 0) IEEZ(_eez).RECOVERY_ADDRESS().call{value: predeployedEther}("")`. It is not a dent in the claim: the manager still determines the destination, the calldata is empty, it fires at most once at construction, and it forwards nothing.
- **R2 — `q4` is correct, and the truth is stronger than the page claims.** `ProxyInfo` field order verified against `IEEZ.sol:157-161`, and the getter flattening in `codeByStep[1]` (`:254-255`) is right. The page's caption is *"isProxy true means the other two fields are real"* (`:240`) — which reads as a convention. Widening the write-site grep to the whole `src/` tree gives **one** write: `EEZBase.sol:169`, `authorizedProxies[proxy] = ProxyInfo(true, originalAddress, originalRollupId);`, against six reads (`EEZ.sol:786`, `:1140`, `:1268`, `EEZL2.sol:223`, `:533`, `:595`), with no `delete` anywhere. And that sole write is the statement immediately after the only `new CrossChainProxy` in the codebase (`:168`), in the same function. So the invariant is structurally guaranteed, not conventional.
- **R4 — `q6` is exhaustive where it claims to be, and its test knows what it is not testing.** `EEZ.sol:785-789` and `:1267-1271` are byte-identical including comments, each is the first statement of its function, and they are exactly the two functions `CrossChainProxy._fallback` calls (`:97`, `:101`). So *"Both proxy entry points open with this check"* is exhaustive, not approximate. The test is four negative cases with an explicit paragraph on why the positive case is absent (`snippets/test/Q6ManagerDirect.t.sol:17-21`): *"faking an entry here would mean either adding a setter that the real contract does not have, or poking storage with vm.store. Both would be testing the fake rather than the protocol."* That instinct, written down where a reader will copy it, is rarer than it should be — and it is the standard the `q8` candidate in Task 11 currently fails.
- **R5 — `q5` is the most rigorously grounded page on the site.** Field order verified against `EEZBase.sol:198-214` element for element, and upstream's own docstring at `:193-197` makes the same load-bearing argument the page makes. All three pinned digests were independently re-derived twice — the second time by writing Keccak-f[1600] from scratch in Python, validated against three published vectors first, because `hashlib.sha3_256` is NIST SHA-3, not keccak, and would have silently mismatched. Baseline `0x6f907866…5cf8fbe1` (`Q5ContentHash.t.sol:43`), swapped `0x9876a218…962dc19f` (`:55`), isStatic `0xb3d426ce…489daa1d` (`:67`) — all three match, 320 bytes / 10 words each. The page's live calculator (`assets/eez-hash.js`), the Foundry test's pinned constants and two outside implementations all agree, so the test's claim to *"pin solc's output against an independent implementation"* is honest. Neither checker can verify any of this.
- **R6 — `q2`'s static/mutating branch is right in both directions.** Copied verbatim from upstream `CrossChainProxy.sol:95-102`: `staticcall` → `staticCrossChainCall`, `call{value:}` → `executeCrossChainCall`. The skill flags mixing those two schemas as *"a subtle, silent error"*; `q2` gets it exactly right. It also keeps the double-encode unwrap (`abi.decode(result, (bytes))`) visible rather than hiding it in a helper, which is the non-obvious line and the one a reader would otherwise get wrong.
- **R7 — the track is scoped to its reader on purpose.** The words *composer*, *entry* and *table* appear nowhere on the dapp track. That is the correct call: app developers never build an execution table, and operational detail dropped unlabeled into app-dev content is how EEZ writing becomes intimidating for no benefit. Score it as a deliberate right, not an omission — the one place it collides with the reader's interest is B1, where the constraint is not operational trivia but the thing that breaks their design.

## The architectural observation — `authorizedProxies` is the identity oracle

`q4` teaches `authorizedProxies` as a convenience lookup: *"One call: `authorizedProxies(someAddress)`"* (`:244`). It is not a lookup. It is the protocol's identity oracle.

It is written at exactly one site (`EEZBase.sol:169`), atomically with the CREATE2 deploy that creates the proxy, and it is the same mapping both manager entry points read to authorise a caller (`EEZ.sol:786`, `:1268`). So:

- the mapping `q4` teaches you to read **is** the thing `q6` says you cannot get past, and
- **is** the check `q3` hand-rolls by re-derivation (W3).

Three consecutive pages circle one storage slot without ever saying it is the same slot. Saying it once — a sentence on `q4`, since that is where the mapping is on screen — would collapse `q3`, `q4` and `q6` from three tricks into one mental model. This is the highest-value edit available on the track, and it is one sentence.

## What the automated layer cannot see here

Four blind spots, all demonstrated by findings above:

1. **A constant's value.** The `5000` defect passed drift, citation and structural checks because the panel shows only `gas: STATIC_CHECK_GAS`, so the number exists in no surface either checker compares. → Task 8.
2. **In-panel `// file:NNN` annotations.** They are prose to every checker. Task 1 found three of them wrong on `pr3`.
3. **Cross-function recombination in COPY output** (W4). `check-panel-drift.py` asks whether each line exists in the snippet; it cannot ask whether the lines came from the same function.
4. **Whether a cited line is the pedagogically right anchor** (W5). `verify-citations.py` proves a cited line exists and still says what it said at the pin. It cannot ask whether it is where the reader should be sent.

One structural gap behind all of this: **`build-llms.py` has no `--check` mode wired into `audit.sh`.** `sync-embedded-snippets.py` guards the HTML copy; nothing guards the generated one. That is exactly how `5000` reached `llms-full.txt:277` and stayed there.

## What could not be verified

- **Solidity's transient-storage slot allocation was deliberately not asserted.** The shipped comment claims only that raw slot 0 is not reserved for the user, which is the part that does not depend on allocator behaviour.
