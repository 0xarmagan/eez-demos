WHY THIS DEMO

K · Sync Blocks

For a node operator (or anyone reading a Rollup0 block explorer) wondering why the block cadence looks the way it does — most blocks are ordinary, but every so often one looks different. This is that scheduling decision, at the level the sequencer actually makes it: not the cross-chain call format itself (demo C) and not the ingress fronts that feed it (demo L).

What you should walk away understanding
  • A Sync block isn't special content bolted onto a normal block — SlotKind::Sync is just a label; whether it actually carries cross-chain work is a separate, per-trigger decision.
  • The trigger is anchored to an L1 head, not a fixed L2 timer: it fires at L1.timestamp + proof_window_open, derived from four config numbers.
  • The schedule never skips a beat — a late trigger or a failed compose still produces a Sync block, just an empty one; cross-chain work waits for the next on-time slot.

the Sync block always ships // sometimes empty
two catches
a.
the trigger itself runs late
If the proof bundle can't reach the relay before the next L1 slot, sync_block_misses_l1_slot catches it and the Sequencer commits an empty Sync block under SyncSlotMode::Empty. Nothing is lost — the held cross-chain work just waits for the next on-time slot.
b.
the compose step itself errors
If compose_cross_chain_batch fails (a simulation error, say), the composer pushes the whole held batch back onto the pool and returns None — the Sequencer still commits a fallback Sync block, just without the cross-chain content this slot.
Either way the schedule never skips a beat. What happens if a Sync block's postBatch then fails to land on L1 — after it's already been committed to L2 — is a different question: see demo M · Commit-First, Repair-If-Needed.
